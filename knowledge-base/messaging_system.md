# Direct Messaging and Structured Mailbox System

## 1. Introduction
Communication is the lifeblood of the FounderX platform. However, to prevent the spam and low-quality pitches that plague generic professional networks, FounderX implements a gated communication model. 

Rather than allowing unrestricted outreach, the platform enforces strict security checks. It splits communication into two distinct systems:
1. **The Mailbox System**: Used for structured, operational requests (e.g., job applications, co-founder inquiries, investment proposals) that require recipient action.
2. **Direct Messaging (Chat)**: A real-time, threaded chat system that is unlocked *only* after a relationship has been authorized via the gated connection engine.

This document describes the messaging rules, communication flows, notifications, and privacy controls available on the platform.

---

## 2. Direct Messaging Rules & Authorization Check
Direct messaging is managed by `/api/messages`. To send a message or start a conversation, the sender and recipient must pass the connection check.

### A. The Chat Permissions Engine
Direct chat is unlocked if and only if at least one of the following criteria is met:
1. **Mutual Follow**: Both users follow each other's personal profiles.
2. **Shared Startup Team**: Both users belong to the team list of the same startup profile.
3. **Accepted Investment Request**: A founder has accepted an investor's interest request.
4. **Accepted Application/Role Request**: A founder has accepted a job application or custom co-founder role request.

If none of these criteria are met, the message API returns a `400 Bad Request` with the error message:
`"You must follow each other, be in the same startup team, have an accepted investment request, or have an accepted job application to start chatting."`

## 3. Communication Workflows
The platform supports several distinct communication pathways:

### A. Founder-to-Founder Communication
* **Purpose**: Peer support, co-founder matching, sharing resources, and strategic collaboration.
* **Workflow**:
  1. Founder A visits the profile of Founder B and clicks "Connect" (which follows Founder B).
  2. Founder B reviews Founder A's profile and follows back, establishing a **Mutual Follow**.
  3. Direct messaging is unlocked. Either founder can now initiate a conversation at `/messages`.

### B. Founder-to-Investor Communication
* **Purpose**: Pitching, sharing financials, and completing due diligence.
* **Workflow**:
  1. An Investor discovers a startup and submits an **Investment Interest Request** containing details on ticket size and investment parameters.
  2. The request appears in the founder's Mailbox.
  3. The founder reviews the request and clicks **Accept**.
  4. An **InvestorStartupConnection** is established, direct messaging is unlocked, and the **Investment Room** is created.
  5. The founder and investor can now chat directly in the Investment Room sidebar.

### C. Seeker-to-Founder Communication
* **Purpose**: Job inquiries and team matching.
* **Workflow**:
  1. A Job Seeker applies for an open role or submits a custom co-founder role request.
  2. The founder receives a Mail item in their inbox.
  3. The founder reviews the application. Clicking **Connect** accepts the application and unlocks direct messaging with the candidate.

## 4. Gated Mailbox System
Operational requests land in the **Mailbox System** rather than a chat feed. The Mailbox (accessible via `/inbox`) handles structured messages that require explicit decisions.

### A. Mail Types
* `investment_request`: Sent when an investor wants to fund a startup.
* `application_request`: Sent when a job seeker applies for an active job opening.
* `cofounder_request`: Sent when a professional submits a custom role request.
* `founder_update`: Sent automatically to connected investors when a founder posts a startup traction update.
* `status_update`: Generated by the system to notify users when their applications or requests are accepted or rejected.

### B. Mail Actions
Each mail item has associated actions:
* **Accept**: Updates the underlying request (e.g., marks a job application as accepted, adding the candidate to the startup's team list, or establishing an investor connection).
* **Reject**: Declines the request, notifying the sender.
* **Delete (Soft Delete)**: Moves the mail item from the `inbox` list to the `trash` list. It can be permanently deleted or restored later.

## 5. In-App Messaging Features
Once chat is unlocked, users have access to several communication features:
* **Real-time Messaging**: Powered by socket.io to deliver messages instantly with typing indicators.
* **Read Receipts**: Tracks which participants have read each message (`readBy` array).
* **Message Editing**: Users can edit their messages within a 15-minute window.
* **Message Deletion**: Users can delete messages "for me only" or "for everyone" (within a 1-hour window).
* **Reactions**: Add emoji reactions directly to message bubbles to express quick feedback.
* **Media & Attachments**: Uploading images, documents, and pitch files directly in the chat panel.

## 6. Privacy & Security Controls
To give users control over their communication experience, FounderX provides privacy settings managed via `/settings`:

### A. Privacy Controls
* **Message Permissions**: Users can restrict who can send them connection requests:
  * `everyone`: Anyone on the platform.
  * `verified_only`: Restricted to verified profiles.
  * `mutuals_only`: Restricted to users with shared connections.
* **Profile Visibility**: Founders and investors can set their profile visibility to `public` or `private` (restricting access to authenticated users only).
* **Block List**: Users can block specific accounts via `/api/users/block/:id`. If blocked:
  1. The blocked user cannot send messages or mail items.
  2. The blocked user cannot view the other party's profile or startups.
  3. Any active chats are locked and return a `403 Forbidden` response.
* **Data Security & Escapes**: The system scans chat inputs and uploaded documents for prompt injection attacks and malicious content, ensuring a secure communication environment.
